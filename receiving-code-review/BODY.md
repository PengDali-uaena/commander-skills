# 接收代码评审

用于你**已经收到评审意见**时（对话里、PR 里、子 agent 输出里）。这不是发起评审——发起走 `requesting-code-review`。

代码评审要的是技术判断，不是情绪表演。

**核心原则**：先验证再实现；不确定就问；技术正确优先于社交舒适。

## 回应流程

```
收到评审意见时：

1. 读：完整读完，先不反应
2. 理解：用自己的话复述要求（或直接问）
3. 验证：对着代码库现状核
4. 判断：对 THIS 代码库技术上成立吗
5. 回应：技术确认，或带理由推回
6. 实现：一次一条，每条都测
```

## 禁止的回应

用户规则通常也禁止这些等价物：「你说得对」/「谢谢」/ 复述结论 / 先讲修的过程再给结果。

**绝不：**
- 「你完全正确！」（违反用户规则：不奉承、不表演式附和）
- 「这个点很好！」/「反馈很棒！」（表演）
- 「我现在就改」（还没验证之前）

**改成：**
- 复述技术要求
- 问清楚
- 认为错就带技术理由推回
- 直接开干（行动胜于言辞）

## 意见不清楚时

```
只要有一条不清楚：
  停 —— 先什么都别实现
  对不清楚的条目要求澄清

为什么：条目之间可能相关，理解一半 = 改错。
```

**例子：**
```
你的搭档：「修 1-6」
你懂 1、2、3、6，4、5 不清楚。

❌ 错：先改 1、2、3、6，回头再问 4、5
✅ 对：「1、2、3、6 我明白。4 和 5 需要你确认后再动手。」
```

## 按来源区别对待

### 来自你的搭档
- **可信** —— 理解后直接实现
- 范围不清**仍要问**
- 不做表演式附和
- 直接开干，或一句技术确认

### 来自外部评审者
```
实现之前：
  1. 查：对这个代码库技术上成立吗
  2. 查：会破坏现有功能吗
  3. 查：当初为什么这么实现
  4. 查：所有平台 / 版本都成立吗
  5. 查：评审者掌握完整上下文吗

意见看着不对：
  带技术理由推回

不好验证：
  明说：「没有 [X] 我验证不了这一点。要我 [去查 / 问你 / 先按它改]？」

和你搭档先前的决定冲突：
  先停下来和搭档确认
```

**搭档的规矩：**「外部反馈——保持怀疑，但认真核」

### 经子 agent / headless 跑出来的评审

`requesting-code-review` 起的那次 headless 评审、`multi-model-review`、或任何别的 agent 给的反馈，一样算**外部**：先用读文件与只读 `bash`（`git diff`、`rg`、`git log`）核过再动代码。

- 多个模型一致是证据，不是证明；单个模型的结论在你复现之前只是假设。
- 没有 shell 的评审跑不了构建——它说的「看起来没问题」不算验证。
- 项目规则仍然约束你：所在仓的 `AGENTS.md` 限制哪些验收命令时，只用允许的那些。若这条修法没法那样验证，就明说，不偷偷跑被禁的命令。

## 「做得更正式一点」先过 YAGNI

```
评审建议「正确实现」时：
  grep 代码库看实际调用

  没人用：「这个端点没人调。删掉（YAGNI）？」
  有人用：那就正确实现
```

**搭档的规矩：**「你和 reviewer 都对我负责。不需要的功能就别加。」

## 实现顺序

```
多条意见时：
  1. 先把不清楚的澄清掉
  2. 再按这个顺序改：
     - 阻塞项（会崩、安全问题）
     - 简单修（拼写、import）
     - 复杂修（重构、逻辑）
  3. 每条单独测
  4. 确认没有回归
```

## 什么时候该推回去

这些情况推回去：
- 建议会破坏现有功能
- 评审者缺上下文
- 违反 YAGNI（没人用的功能）
- 对这个技术栈不成立
- 有历史 / 兼容原因
- 和搭档的架构决定冲突

**怎么推：**
- 讲技术理由，不护短
- 问具体问题
- 拿跑得通的测试 / 代码说话
- 架构层面的事拉搭档进来

**不好意思当面推的时候，说这句**：「有点不对劲，我先核实一遍。」

## 意见确实对的时候

一句话：说「改好了。」+ 一句说明改了什么，或直接改让代码说话。禁止「你完全正确」「这个点很好」「谢谢」——行动说话，代码就是听进去了的证明。

## 推错了怎么收

一句话：平静陈述纠正（「你是对的，我查了 [X]，确实 [Y]，这就改」），不写长篇道歉、不解释自己为什么推，然后往下走。

## 常见错误

| 错误 | 改法 |
|---------|-----|
| 表演式附和 | 复述要求，或直接动手 |
| 不看代码就改 | 先对代码库核实 |
| 批量改完不测 | 一次一条，每条都测 |
| 默认评审者是对的 | 先查会不会破坏东西 |
| 不敢推回 | 技术正确 > 舒服 |
| 只实现一部分 | 先把所有条目澄清 |
| 验证不了还往下走 | 说明限制，问方向 |

## GitHub 行内评论

回复 GitHub 的行内评审评论时，在该评论的 thread 里回（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`），不要发成 PR 顶层评论。

## 底线

**外部反馈＝待评估的建议，不是必须执行的命令。**

先验证，再质疑，最后实现。

不表演式附和，技术严谨到底。
