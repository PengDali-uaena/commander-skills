# bugfix-probe

定位故障：先按假设读代码。证据不足就加诊断日志并停下，把筛选交给用户。日志或堆栈已经指到具体行时，才做最小修复并写根因。

## 启动

写下现象、复现路径、平台。缺现象或路径时最多问 2 个问题，然后按已有信息继续，并在阶段性结论里标明假设。

写下 1～3 条可证伪假设，每条对应要读的文件或符号。用户点名的路径和堆栈里的文件优先。清单外的目录不扫。

## 读代码

- 禁止无关键词的全仓搜索当第一步。
- 假设清单外最多再读 5 个文件。每多读一个，须能说出它和哪条假设有关。
- 假设的支持、否定、待定留在工具过程里。可见回复不写假设表，除非用户本条说「看假设表」或「展开假设」。
- 只是「代码看起来像」：写入阶段性结论，不写根因，不改业务逻辑。多条待定分支按可能性排序，最可能的写在最前；不按代码行号或文件顺序平铺。
- 日志或堆栈已经证明因果，或已经指到具体行：可以做最小修复，并写根因。改动遵守当前仓库规范。

## 诊断日志

证据还不够时必须写入代码，不能只在回复里建议。

- 一次排查一个主 Tag。先看正在改的文件和仓库里现有日志怎么写，沿用那个 API，级别用 debug。
- 仓库没有日志设施时，用该平台自带的 debug 输出，不新增依赖。
- 没有既有排查 Tag 时，用 `Probe/<模块>`。
- 跨端链路（Flutter / H5 / Android / iOS）用同一个主 Tag 串起来，各端字面量保持一致，筛选按端分列。
- 每条日志带 `phase=<token>`。token 为 snake_case，本任务内不重复，并且会出现在筛选里。
- 不打无 Tag 的 print，不把整个对象打出来。
- 用户要求线上也能看到时才用 info 或 warning，并在阶段性结论里写明事后要收日志。

用户已经贴了日志仍缺分支：写明现有日志排除了什么、缺哪条，并按下节「一次埋齐」补一轮。

## 一次埋齐（不要一轮加一条）

用户复现一次成本很高；「加一条日志 → 等日志 → 再猜一层」是本技能最常见的失误。

- 加日志前先列出「要定因需要哪些字段」，本轮一次覆盖全部待定分支：每条假设至少一处 `phase`，不要分轮。
- 一轮日志回来仍分不清分支时，第二轮必须一次补齐所有剩余判据，并在回复里给出判读：哪个 `phase` / 字段取什么值对应哪种结论。缺判读的回复视为没交付。
- 能加日志就别让用户做对照实验；必须做对照时，写清「正常态 / 异常态各操作一次，两次各看哪个字段」。
- 同一问题连续 3 轮没有结论：停下来换方法（对照实验、改读代码、把边界交回 Native / 后端），不要再加第 4 条日志。
- 日志已经指向具体行时不要再补日志，直接给根因和最小修复。

## 筛选

只输出实际要抓的平台。用户点了名就只给该平台。没点名时：仓库明显只有 Web 就给 Web；明显只有 Apple 就给 iOS；否则 Android 和 iOS 都给。不编造 subsystem 或 category。

- Android 一行。主 Tag 和本轮 phase 用 `|` 连起来，`|` 左右没有空格。`|` 表示或。这行用于 logcat 搜索框，也是 `adb logcat -e` 的正则。
- iOS 每个要搜的字符串单独一行，至少一行主 Tag。phase 和 Tag 总会出现在同一行时，不要再拆 phase。用户本条说明 iOS 已打开 Regex 时，改为一行 `- iOS Regex：`，用 `|` 连接，不再拆开。
- Web 与 iOS 相同，前缀是 `- Web：`。浏览器控制台按子串匹配。

筛选里的每个 token 必须和代码里的字面量一致。

## 可见回复

每行一个字段，按 commander「字段块版式」：字段名加粗（`- **阶段性结论**：……`），**字段之间空一行**，值内最多再加粗 2 处判定词。这里每个字段自成一组。不用代码围栏，块外不加文字。路径、数字、Tag、token 写全。

阶段性结论有多条分支时重复该字段，连续多行、不空行，按可能性从高到低；禁止把多个分支塞进一条。

证据不足：

```
- **阶段性结论**：……

- **Android**：Tag|phase_a|phase_b

- **iOS**：Tag

- **Web**：Tag

- **操作路径**：……

- **判读**：出现 `phase_a` 且 `hasX: false` = 结论 A；只有 `phase_b` = 结论 B

- **改动**：……

- **Tag**：Tag
```

没有的平台整行省略；iOS 或 Web 有多个字符串就重复对应行；没有判读需求就省略判读行。

已经证明根因：

```
- **阶段性结论**：……

- **根因**：……

- **Tag**：Tag

- **改动**：……
```

没有改仓库就省略改动。本轮没有诊断 Tag 就省略 Tag。有根因时不输出筛选和操作路径。

用户说「看假设表」或「展开假设」：字段块之后最多 3 行 `- 假设：`，并列出 phase 名。

## 示例

示例只说明形状。Tag、token、路径以当前仓库代码为准。

```
- **阶段性结论**：列表为空，读代码像是回调早于订阅，日志还没证实。

- **Android**：Probe/Inbox|phase_subscribe|phase_callback

- **iOS**：Probe/Inbox

- **操作路径**：杀进程冷启进列表，停 10 秒，把筛选结果贴回来。

- **判读**：`phase_callback` 早于 `phase_subscribe` = 订阅晚于回调；顺序正常 = 假设不成立。

- **改动**：InboxController 订阅前后各一条 debug。

- **Tag**：Probe/Inbox
```
