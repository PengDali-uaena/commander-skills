# multi-model-plan

用户要一份能落地的方案，或不信手上的方案（有漏项、假设没证据）时：多个模型独立出方案或盲审同一份草稿，主 agent 逐条校准成 v2。

只在用户显式点名本 skill（或本侧等价显式加载语法，见 `{{SRC_ROOT}}/TOOL-MAP.md`）或明确要求「多模型出方案 / 方案对审 / 校准方案」时使用。默认**不改代码、不落盘**；用户要可执行交接稿时走 `coding-handoff-plan`。

## 1) 定模式

- **盲审（默认，已有 v1）**：prompt = brief + v1 全文 + 五问。reviewer 只看 brief 和 v1，看不到彼此意见。
- **并发出稿（没有草稿，或用户说「这个方案不可信 / 重新想」）**：prompt 里只放 brief 和五问，不放任何人的草稿。锚定会让三家收敛成一家，真分歧就看不出来了。
- 拿不准就问一句「审现有方案，还是让它们各自出方案」，问完即停，不要自己挑一个就开跑。

## 2) 写 brief（比方案本身更重要）

reviewer 没有工具，brief 里没写的它只能猜；猜出来的缺口会和真缺口混在一起，校准时分不开。

- 必含：目标与验收标准、硬约束（平台 / 版本 / 不能改的模块 / 不新增的依赖）、已知事实（`file:line`、接口名、报错原文、数据形状）、已知不确定项。
- 事实与推测分两段写；没有证据的写 `（推测）`，不让 reviewer 把猜测当约束。
- 体积：brief 控制在约 120KB 以内；跨 30 个以上文件时压成「子系统 + 约束」清单，不整包塞源码。输入不是瓶颈（实测 137KB 输入 6～14 秒返回），输出长度和工具轮次才是。

## 3) 选模型

- 一次 `pi --list-models` + 一次 `pi auth check --provider <p>`，不逐个 slug 试跑，准备阶段不烧预算。
- 内联列编号 + slug，中性展示：不推荐、不排序、不预选、不省略、不加 "(Recommended)"；`not_ready` 与 403 的不列，写一句「<slug> 已跳过，403 不可用」。
- 默认 2 个、最多 3 个；同厂商同代只留一个，同源模型的意见不增加独立性。
- 用户已指定就直接用；执行时某个 slug 被拒，换最接近的合法 slug 并说明替换了什么。

## 4) 并行跑（无工具 / 硬超时 / 不等齐）

每个 slug 起一个 headless reviewer，只读、前台、并行：

```
pi -p --no-session -nt --no-mcp -nc -ns --mode text \
  --append-system-prompt "You have no tools in this session. Never emit tool calls or tool_call XML; answer directly in markdown." \
  --model <provider/model> < /tmp/mmp-<ts>/prompt.md
```

- **禁止给工具**：不写 `--tools`、不加 `-t read,bash`，prompt 里也不写「可以读仓库 / 可以跑命令」。实测给 `read,bash` 的那次 13 分钟只出 5.3KB，禁工具同体量输入 6 秒返回；工具还会让结论跑到方案之外。
- **每个模型 300s 硬超时**：macOS 没有 `timeout`，用 codemode `tools.bash` 的 `timeout`，或 `gtimeout`，或后台起 + 到点 `kill`。到点记「no response (timeout)」，不重跑、不换模型补位。
- **必须并行**：同一轮 `codemode` 里 `Promise.allSettled` 一次发出；禁止逐个等待，禁止 `sleep 120/180` 等最慢的那个。
- **分批校准**：拿到 ≥2 份就先出 v2，剩下的在 deadline（整轮 6 分钟）内补；只有 1 份时照实写「另外 N 个未回」，不自己补位凑成「多模型」。
- 失败（403 / 超时 / 空输出）只记 no response，不影响其他 reviewer。

`prompt.md` 另须写死：

- **输出预算**：最多 8 条，每条 `[P0|P1|P2] 结论 → 依据 → 影响`，最多 3 句；不复述 brief、不写总结段。不设上限时单个模型会吐 12KB，按 30～120 字符/秒算就是 2～7 分钟纯生成。
- **必答五问**（不写死各家会自选角度，合并时对不齐）：
  1. 漏了什么：缺的边界、状态、失败路径、依赖顺序；
  2. 哪条假设没有证据；
  3. 顺序或依赖错在哪，会先卡在哪一步；
  4. 最坏情况是什么，怎么回滚；
  5. 有没有更简单的做法，能删掉哪几步。
- 结论必须落到 `file:line`、接口、报错原文或可复现步骤，落不到的写 `（推测）`；没有问题就明确写 no findings。

## 5) 校准（主 agent 做，最容易被跳过的一步）

- 逐条判定：采纳 / 部分采纳 / 不采纳，每条带一句理由；不采纳必须给理由，不许沉默丢弃。
- **证据优先于票数**：两个模型同指一处但都没有证据，仍然只是 `（推测）`；一条结论只有在能落到 `file:line`、接口、报错原文或可复现步骤时，才升级成改动。
- 分歧写 `2:1` / `1:1` 并附各自依据，不写「多数模型认为」收口，票数当不了证据。
- 同一份方案只跑一轮；分歧落在关键路径或用户要求时才补第二轮，且只把分歧点重新分发，不重跑整包。第三轮不做。
- v2 必须能回答：改了什么（旧 → 新）、哪几条没采纳、哪些假设仍未验证。
- **记下校准质量**：本轮回了几份 / 发了几份（`3/3` / `2/3` / `1/3·偏低`），加上没回的 `<slug>`，写进 §6 判定组；`1/3` 时连自己没复核的条目一起列。

## 6) 交付

默认只在回复里给 v2，不改代码、不落盘、不自作主张跑测试。用户要可执行稿 → `coding-handoff-plan`。

回复用字段块（一行一个字段，都以 `- ` 开头，字段名加粗，组间空行）。第一组是判定：读完这几栏就能决定要不要动手，不用先读方案。

- **可执行性**：`是` / `否` / `需补 N 条`，三选一
- **阻断原因**：仅 `否` 时写，一句说清卡在哪
- **待补条目**：仅 `需补 N 条` 时写，一条一行，条数必须与 N 一致
- **最大风险步**：v2 执行时最先卡住的那一步，一句；不写「整体风险」这类概括
- **缺证据**：挡在可执行性前面的缺证条目（`未证实` 里影响动手的那几条）；没有就写 `无`

- **校准质量**：`3/3` / `2/3` / `1/3·偏低`，后接没回的 `<slug>` 列表

判定口径：

- 判定只服证据：动手门槛看条目能不能落到 `file:line`、接口、报错原文或可复现步骤（见 §5），不看票数；单票但有证据的条目照样算数。
- `1/3` 时「缺证据」必填：没回的 slug + 自己没复核的条目。不因「只有 1 份」就标 `是`，也不因票少自动降成 `否`。
- 分歧落在「最大风险步」上时，可执行性不写 `是`，写 `需补 N 条` 并列出补哪条。
- 判定组与「结论」矛盾时以判定组为准。

- **结论**：v2 一句话定位 + 采纳 N / 不采纳 M / 分歧 K，不得与「可执行性」矛盾
- **方案**：核心做法一条一行；改动的写 `旧 → 新`
- **采纳**：`<model>` — 条目 + 落点（`file:line`）
- **不采纳**：条目 — 理由
- **分歧**：`2:1` / `1:1` + 各自依据
- **未证实**：假设 + 怎么验
- **下一步**：落交接稿 / 直接开发 / 只对分歧点补一轮

## 不做什么

- 不改代码、不写文件、不跑测试，除非用户另说。
- 不让同一个模型扮两个角色凑「多模型」；只回 1 份就写 1 份。
- 不把 reviewer 原话照抄成结论：没经过校准的输出只是素材。
- 不为了「显得完整」编 brief 里没有的步骤；缺的信息写 `（待验证）`。
