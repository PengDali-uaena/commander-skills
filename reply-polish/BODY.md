# reply-polish

排版收口层。默认收口已并进 commander 硬约束第 5、6 条与 `AGENTS.md`「可见回复」，本文件只在用户点名或说「整理格式 / 输出太乱 / 太长没重点」时使用。本层不选产物、不读仓库、不改判定，只动结构、长度和引用方式。

## 与下游 skill 的关系

1. 产物与结论以选中的 skill 为准；本层只改呈现，遇到判定冲突不改判定。
2. 下游写死的版式优先：「仅两行」「字段块一行一个字段」「bugfix-probe 必留 Tag 与筛选语句」照旧，本层不并字段、不删原文、不破行数上限。
3. 本层只补三类东西：首行总判定、并列项分点、引用与强调降噪。补完仍须落在下游篇幅预算内。
4. 下游输出已经合格就不重写，只做缺口检查。

## 一、总判定（总结性言论）

- 第一行一句加粗判定，读者只看这一行就知道结论；不写背景、不写过程、不写「我先看了」。
- 这句针对整条消息，不是只针对第一段。
- 每点的首句各自成结论，首行不替它们兜底。
- 长答复（≥3 点或超过 10 行）末尾可用**一行**给「所以 / 下一步」；不复述上面已说过的点，不写总结段。
- 字段块类回复不写块外首句，结论落在第一个字段。

## 二、分点（并列项必须拆行）

触发：≥2 个原因、≥2 个方案、≥2 个步骤、≥2 个位置或文件、≥2 条待办、≥2 个缺陷。

- 一条一行，形如 `- **该点结论**：一句解释`；首句就是该点的答案，后面才是理由或做法。
- 细节多时解释另起一行缩进，不把两件事挤进一行，也不缩回一大段。
- 只有 1 件事写段落，不为排版硬拆列表；列表每条长度差太多时先合并同类项。
- 拆分后同一层级只用一种符号（`-` 或 `1.`），不混用。

## 三、引用降噪（不出现裸 URL）

- 本地文件写相对路径的行内代码，如 `lib/features/checkout/x.dart:42`；不写 `file:///`、不写 `~/`、不写整条绝对路径。
- 同一路径一条回复只出现一次；后续用「该文件」「上面那个 service」指代。
- commit、PR、issue、文档：给最短可定位标识（短 SHA、编号、模块名）。用户要复制走（curl、接口文档、发给同事的链接）时才给完整 URL。
- Tag、日志行、报错原文按字面抄，不套 URL、不加 `http(s)://`、不把整段 logcat 贴进来。
- 能定位就不引用：说明某段代码时描述位置，比贴一屏原文更有用。

## 四、强调（加粗优先）

- 加粗只落在判定词、关键数字、反转点（`旧 → 新`）、必须照做的动作；一条回复合计不超过 3～5 处。
- 手段按可用性排：**加粗** > `行内代码` > 引用块。纯文本/终端场景没有颜色，不写 ANSI 转义、HTML `<span>`、拿 emoji 当高亮。
- 整句加粗等于没加粗；标题层级不要超过两级。

## 发出前自检

1. 首行是不是一句能独立成立的判定？
2. 有多条并列却写成了段落？每条首句是不是结论、是不是各占一行？
3. 还有没有裸 URL、绝对路径、可省掉的引用？
4. 拆点后有没有超出下游 skill 的行数上限，或把它的字段块拆散？
