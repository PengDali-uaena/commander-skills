# branch-merge

合并分两步：先讲清冲突双方各自要保住什么，给出合并意见，然后停。用户明确确认后，才按该意见解决冲突并完成合并。

## 确认前

读冲突本身，不改文件，不执行 `git merge`、`git add`、`git commit`、`git checkout --ours/--theirs`。

- 已有冲突：只读冲突文件里的冲突段，以及看懂意图所需的紧邻代码。分支名用当前合并的双方。
- 还没开始合并：只读用户点名的两个分支在重叠处的差异。没有点名就问一句是哪两个分支，然后停。
- 意图写行为，不复述整段 diff。符号、路径、分支名写全。

可见回复只有这些行，按 commander「字段块版式」：都以 `- ` 开头，字段名加粗，组内字段紧排不空行，**冲突点与冲突点之间空一行**。不用代码围栏，块外不加首句和总结段。

一个冲突点一组，组内顺序固定为 冲突 → 当前分支意图 → 目标分支意图 → 合并意见，五字段同级，不给 `冲突` 加编号或子级。待确认 收口，单独一行，与最后一组空一行。

```
- **冲突**：路径或符号
- **当前分支意图**：`<当前分支>` 这边要保住的行为
- **目标分支意图**：`<目标分支>` 那边要保住的行为
- **合并意见**：怎么合，保留哪边的行为，或如何拼在一起

- **冲突**：第二个路径或符号
- **当前分支意图**：……
- **目标分支意图**：……
- **合并意见**：……

- **待确认**：确认后才改文件并完成合并
```

本轮到此为止。

## 确认后

只在用户明确确认这条合并意见时执行。用户改了意见但没确认：按新意见重写上面的字段，仍然不执行。同一条消息里既改了意见又明确确认：按新意见执行。

- 只落实已经写出的合并意见，不顺手改别的代码。
- 清掉冲突标记，把解决后的文件纳入暂存。
- 合并已经在进行：用 Git 默认合并说明完成这次合并，不另写 `type(module): description` 消息。
- 还没开始合并：按确认的两个分支执行合并；中途出现意见没覆盖的新冲突就停下，回到「确认前」，不猜。
- 不 push，不使用 `--no-verify`，不做 force 或硬重置。

执行后的可见回复：

```
- **已合并**：按哪条意见，动了哪些路径
- **结果**：合并完成，或停在哪一个新冲突
```
