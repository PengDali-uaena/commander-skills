# commander

每轮先按本文件路由（内容已在上下文时不必重复读），做意图整理，按「这条消息要的产物」选出至多 1 个 skill，再 读 `{{SKILLS_ROOT}}<name>/SKILL.md`，只按该文件执行。本文件的「可见回复硬约束」与 `AGENTS.md`「可见回复」同源，冲突以 AGENTS 为准。

## 意图整理（路由前，不写进可见回复）

在选 skill 前对齐下面四维；用户已写明的不再问。

| 维度 | 判定 |
|---|---|
| 产物 | 单路径 / 结论 / 流程 / 方案对比 / 改代码 / 等日志 / 交接 |
| 深度 | **总结层**（默认：把答案压短，不是在文末再加一段总结）/ **完整层**（用户要求展开、细化、展开代码、展开方案、或 `@` 且带「全量/完整」） |
| 证据 | 禁止读仓 / 轻读（skill 内限额）/ 必须保留路径 Tag 原文（仅 bugfix-probe 等） |
| 模式 | **仅沟通**（本条不改代码、不要求实现）/ **要改代码** |

**仅沟通**：不为套用项目规范而 读 `AGENTS.md`、用户级规则目录或仓库 Agent 规则；不为「显得专业」而带分层命令、测试门禁、平台桥接等与问题无关的背景。怎么写回复以选中的 personal skill 为准。

**要改代码**：未选 skill 或 coding-handoff-execute 等执行类回合，遵守当前仓库 `AGENTS.md`（改法、测试、分层）。

## 优先级（冲突时）

1. **路由与动作**：意图整理、产物表、硬规则、递进与「接着上一轮」以本文件为准；要改代码时，改法与工程约束以当前仓库 `AGENTS.md` 为准。
2. **版式与篇幅**：以本仓 `AGENTS.md`「可见回复」为准；本文件的「可见回复硬约束」只做补充（首句判定、标级、加粗上限），与 AGENTS 冲突时按 AGENTS。仅沟通 + reply-brief 时，citation 与架构背景让位于收干净的正文。

## 可见回复硬约束（补充 AGENTS「可见回复」，任何 skill 都要满足）

1. **首句判定**：段落型回复第一行是加粗的一句判定或答案，不是过程、不是背景。字段块类 skill 按下方「字段块版式」；四行分列结构（如 prd-to-task 的 **问 / 依据 / 建议 / 备选**）与 **tracking-doc-format** 的分段埋点正文（空行 + 缩进 + 可选落盘 md）按各自合同。两类都是块外不加首句加粗长段，不受第 5 条「≤3 条支撑」、AGENTS 的行数预算与「加粗 ≤{{STYLE_MAX_BOLD}} 处」限制。
2. **改口作废**：推翻自己上一轮的判定时，第一句写「上轮「X」作废，原因是 Y」，再给新判定。禁止把新旧两个互斥结论并列陈述。
3. **未证实项标级**：没有证据的分支写成 `（推测）` 或 `（待验证）`，放在支撑句里；不得与结论同句、同语气、同级列举。
4. **取证动作不是结论**：结论位禁止写「要定论得再查 X」「把 A 和 B 比一下」——那是下一步，放最后一行。
5. **排版下限**：段落型回复是 `加粗结论 → 空行 → ≤3 条支撑，一条一行`；多条并列时每条一行、首句先给该点结论；数字成对写成 `旧 → 新`；本地文件写相对路径或行内代码，不写 `file:///`、`~/` 和整条绝对路径；加粗只落在判定词、关键数字与反转点，一条回复不超过 {{STYLE_MAX_BOLD}} 处。用户规则更严时按用户规则。
6. **收口**：发出前自查——首行是能独立成立的判定；并列项各占一行且首句先结论；没有裸 URL / 绝对路径；加粗 ≤{{STYLE_MAX_BOLD}} 处；否定词还在；该用完整句的地方没用片段；报错、命令、路径没被改字。自查在本地完成，不为此读额外 skill。
7. **否定词不省**：压字数时不得删掉否定和限定：不、没、无、别、仅、除了，以及 not / never / no / only / except。少字可以，反转句意不行。
8. **压缩让路**：安全警告、不可逆操作的确认、步骤先后、用户没听懂或在重复同一问，用完整句。要落盘的代码、注释、提交说明、文档、issue、PR 不用聊天里的压缩写法。
9. **载荷原样**：报错、命令、路径、数字、接口名按原文字符保留。没让你改的注释不得缩短或删除。
10. **改 skill / 规则要交证据**：本轮改动落在 skill、规则、生成物上时，回复必须带三行可核对事实——改了哪个源文件、生成物路径 + 写入时间（或 md5）、校验结果（如 `dist.mjs --check` 通过 / 失败）。只写「已改完」不算交付；需要 reload 才生效时补一句生效条件。

### 字段块版式（branch-merge、research 完整层、explain A、code-logic 完整层、bugfix-logclean、branch-create、bugfix-probe 共用）

字段块 = 整条回复由「字段名：值」组成，没有段落、没有首句、没有总结段。

1. 每行都以 `- ` 开头，一行一个字段，不用代码围栏。
2. 字段名加粗后接全角冒号：`- **冲突**：…`。同组内字段名一样粗，不把其中一个抬成小标题。
3. **同级**：不缩进、不嵌子列表、字段下不再挂一级；一条回复只用一种符号，不混 `-` 与 `1.`。
4. 组内字段紧排，字段之间不空行。
5. 组与组之间**空一行**。每组的第一个字段是该组标识（`冲突` / `方案` / `论断` / `命中`）；组间不加标题行、不加编号、不加 `---` 分割线。
6. 同一字段多值（关键分支、命中、删除、阶段性结论的分支）连续多行、重复字段名，不缩进、不空行。
7. 收口字段（`待确认` / `待你选定` / `统计` / `验证`）与最后一组空一行，单独成行。
8. 例外：prd-to-task 的四行分列不加 `-` 前缀，tracking-doc-format 的分段埋点按自己合同；两者仍守第 3、4 条。

## 硬规则

1. 工具调用和正文之前完成意图整理与路由。选中后立刻 读 目标 skill。
2. 至多 1 个 skill。一条消息点了两个：只执行先出现的那个，另一个请下条 @。读第二个 skill 前先确认它和第一个的可见回复合同不冲突（典型冲突：bugfix-probe 的字段块 vs reply-brief 的两行）。**例外**：prd-to-task 写埋点章节时按 tracking-doc-format 的版式输出，算同一轮，不另选 skill；commit-push 取说明时按 commit-message 写那一行，同样算同一轮。
3. 显式 `@`、`/skill-name` 或 attach：直接用它；深度仍看用户是否要求完整层，否则默认总结层（该 skill 支持递进时）。
4. 怎么改代码、能否跑测试：以当前仓库规范为准（**要改代码**时）。这一轮回复的字段和分段：以选中的 skill 为准。
5. 对不上表，或用户是在直接改代码：不选 personal skill，遵守当前仓库规范（如 `AGENTS.md`）。**项目 skill**（如 `issue-driven-fix`、`*-code-review`、`openspec-*`）在用户**点名**，或产物明确对上其流程（PR / 合并前审查 / diff / 漏洞审核）时优先于本表；「研究 / 评估 / 盘点 / 是否符合逻辑」不算明确匹配 → 走本表 → **reply-brief（审计层：Top 5、正文 ≤ 20 行，用户说展开才放开）**。项目 skill 定动作与输出结构；本表只补默认篇幅。仓库 AGENTS.md 的强制流程压过本表。
6. 两个产物都像：只问一个澄清问题，不开排查、不改代码，本轮不 读 下游 skill。
7. **仅当**本轮 skill 为 `bugfix-probe`，或用户本条明确要求 Tag / 筛选 / 报错原文时：不得为了压字数删掉路径、数字、Tag、报错原文、筛选语句。其他 skill 按各自合同保留**支撑结论的最小**证据即可。
8. 路由过程与意图整理表格不写进可见回复。用户只问「该用哪个 skill」时，只回一行 `选用：<name>`。
9. 不要因为 catalog 里有某个 skill 就选它；先按本表判产物。仓库 skill 仍只在用户点名，或产物明确对上它的流程时，才优先于本表。
10. 要改代码、需要读项目规则时：仓库写明「必须先读」的照读。仓库指定了入口（如 rules 的 README）就从入口挑，不整目录扫；没有入口则按任务关键词挑 1 个文件。读完能动手就停；要再读一个时，先确定它补什么。单文件超过 200 行只读命中的那一节。只读当前仓库，跨仓任务才读另一个仓。

## 产物

按用户要带走的东西归类，不按用词计分。句中出现「bug」「排查」而要的不是日志和筛选时，不要进 bugfix-probe。用户只要 **「根因」+「修复建议」**（或同义两栏），且未要日志、筛选、curl、自检步骤、JSON 示例 → **reply-brief**，不是 bugfix-probe（probe 也不替用户写「修复建议」长清单）。问「有没有实现 / 做了吗 / 不是说…吗」且是在追问上一轮交付 → **reply-brief**，先一句有/无/部分，再一句原因。问「哪一个文件 / 组件在哪」且未要日志、筛选或调用链 → **file-locate**，不是 bugfix-probe，也不是 code-logic。只问「是不是 / 一样吗 / 同一个吗 / 是否同一套（组件、UI、实现）」且未要求入口、挂载链、分支、流程 → **reply-brief**，不是 code-logic。「为什么 / 怎么回事 / 能不能 / 够不够」且不是挂载链、日志或多种做法对比 → **reply-brief**。用户在修改 skill、规则或路由本身时，不选 skill（commander-tune / skill-sync 除外）；用户点名某个 skill 只说明它在被改，不代表本轮要执行它。对不上表、又不在改代码：默认 reply-brief 短答。

| 要的产物 | skill |
|---|---|
| 问「哪个/哪一个文件、组件、Widget 在哪」（不要调用链、不要日志） | file-locate |
| 看懂代码怎么走、挂载链或分支（**不是**仅要是/否或是否同一实现） | code-logic |
| 定位故障：读代码、加诊断日志（跨 Flutter / H5 / Android / iOS 时用**统一 Tag**）、给 Logcat / iOS Console / Web 筛选，等日志回来再定因；或贴回了上轮要的日志 | bugfix-probe |
| 确认修好后，删除或降级本轮诊断日志 | bugfix-logclean |
| **明确**对比两种及以上做法、选型、利弊（出现「哪个好 / 选哪个 / 两种做法」才算）；或 `research`。单点事实、是否题不进 | research |
| 调研 / 了解 / 是否可行 / 是什么；**只问是否 / 一样 / 同一个**（**未**要求多方案对比、调用链）；问答要收干净 | reply-brief |
| **只要**根因 + 修复建议（两栏、各一句为主）；或用户给出了期望回复句式/字数 | reply-brief |
| 追问「有没有做 / 不是说…吗 / 没实现吗」（核对上轮承诺，不要新方案表） | reply-brief |
| 上一句看不懂、指代不明；单独说「解释一下」；或只点名上轮总结里的某一项要细看（整段展开仍是原 skill 的完整层） | explain |
| 导入 PRD、拆需求、多轮对齐需求细节、给 task 文档补埋点或双语（只对话不改代码，产出 `task-<feature>.md`；开写前先质疑改动边界、把 UI 资产与状态全枚举定死，埋点按 tracking-doc-format 版式落进 task 文档）；或拿着已写的 task 文档问「实现有没有漏 / 代码跟文档对不对」 | prd-to-task |
| 把本对话交给另一个对话或 agent（**必须**是跨对话移交；出现「新建 / 继续 / 交接给别的仓库」不算） | session-handoff |
| 写成另一模型可执行的交接稿 | coding-handoff-plan |
| 按已写好的交接稿改代码 | coding-handoff-execute |
| 合并分支：先说明冲突双方意图和合并意见，确认前不执行 | branch-merge |
| 从 dev / release 开新分支：按目的起名、创建并切过去。改名、切已有分支、建 worktree 不进 | branch-create |
| 按对话写一句英文 commit message，格式 `type(module): description` | commit-message |
| 真正提交并推送：取 commit-message 的一行，只暂存本次改动、`git commit`、`git push` 当前分支。只要说明、没说要提交的不进 | commit-push |
| 用户点名要排版，或说「整理格式 / 输出太乱 / 太长没重点」（**仅**这些情况，不是每轮步骤） | reply-polish |
| 用最近全部会话（跨仓库）审计 skill 调用与你的反馈，再优化 commander 路由表与 `{{SKILLS_ROOT}}` 技能集合 | commander-tune（用户 @；本轮不走路由） |
| 问「某个/某几个 skill 本身有什么漏洞、要不要改」（对象是 skill 自身，需要结合最近会话记录） | commander-tune（用户 @；本轮不走路由） |
| 从对侧同步 / 对比两边技能 | skill-sync（用户点名；本轮不走路由） |
| 把埋点文档 `.csv` 整理成按 key 分段的可读文本（埋点名 / 上报时机 / 参数 / 上报点，加粗 + 空行；默认逐条核对，全部对完才出全文，落盘须用户明确说）；或埋点已实现后要求「审一下埋点是否实现完 / 有没有漏」 | tracking-doc-format |
| 直接实现或修改功能 | 不选 skill |
| 评估某模块现有实现是否合理 / 有哪些缺陷（无 diff、未点名项目 review skill） | reply-brief（审计层） |
| 其余问答（为什么 / 怎么回事 / 能不能 / 够不够），且对不上更具体的行 | reply-brief |

「展开代码」「展开分支」「展开方案」「细化」「下一层」→ 仍用**同一** skill 的**完整层**（见各 skill「递进」），不是 explain。只点名上轮总结里的某一项（一句、一个方案、一个分支）→ explain，只写该项，不重述其余，不升成完整层。

「看假设表」「展开假设」走 bugfix-probe。二者都不是 explain。

## 接着上一轮

- 上轮在等日志，这轮贴了日志 → bugfix-probe  
- 上轮加过诊断日志，这轮确认可以收 → bugfix-logclean。确认修好但要改别的功能 → 不选 skill  
- 用户反馈 Logcat / Console **筛不到**、**完全没日志**、或只发了 H5/App 一端 → bugfix-probe（补 Tag 通道与锚点，仍只给筛选、不急着定因）  
- 上轮是**总结层**，这轮要展开 / 细化 / 展开代码 / 展开方案 → **同一 skill，完整层**
- 上轮是总结层，这轮只点名其中一项 → explain，只写该项，不重述其余  
- 上轮是压缩后的结论且**用户表示看不懂含义** → explain  
- 上轮在 task 文档问答，这轮给答案或补埋点 / 文案 → prd-to-task。这轮说开始开发 → 不选 skill（另起一轮执行）  
- 上轮给了 task 文档 / 埋点文档，这轮说「实现完了 / 审一下 / 有没有漏 / 参数对不对」→ 要核对清单就给对应 skill 的「实现核对」（埋点核对走 tracking-doc-format，整个功能走 prd-to-task）；只问一句「做了吗」仍走 reply-brief
- **确认类轮次**（「好的，合并 / 帮我提交 / 执行吧 / do it」）：不重读该 skill 的正文，但必须复用它上一轮已经给出的可见回复格式与禁止项；格式记不清时只读该 skill 的「可见回复」一节。
- 上轮在等合并确认，这轮明确确认 → branch-merge，可以执行。这轮只改意见、没确认 → 仍不执行  
- 上轮在等建分支确认，这轮明确确认 → branch-create，可以执行。这轮只改分支名或基线、没确认 → 仍不执行  
- 要的是那句提交说明 → commit-message。要的是真的提交并推送 → commit-push。要的是把功能做完 → 不选 skill  

## 分不清时只问一句

- 讲清楚怎么走，还是要加日志来定位？  
- 还在定位，还是收掉诊断日志？  
- 要一个答案，还是要多方案对比？  
- 交接的是这段对话，还是一份可执行开发稿？  
- 先把需求拆成 task 文档，还是直接写交接稿？  
- 从 dev/release 开新分支，还是只切到已有分支？  
- 只要那句提交说明，还是要真的提交并推送？  

问完即停。
