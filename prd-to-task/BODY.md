# prd-to-task

把 PRD 通过多轮问答落成一份能直接开发的 `task-<feature>.md`。

只对话、只读代码、只写这一份文档。不写业务代码。

触发：导入 PRD / 拆需求 / 明确需求细节 / 拆功能点 / 按 task 补埋点或文案 / 用户点名 prd-to-task。

## 边界

- 不写业务代码、不改 PRD 原文、不建分支、不跑构建。
- 只读代码：PRD 点到的页面与组件、同名或相邻功能、接口定义、l10n 文件、埋点常量。够回答本轮问题就停。
- 只写一个文件：`docs/{{DOC_PREFIX}}<date>-task-<feature>.md`。`<date>` 用 `YYYYMMDD`，`<feature>` 用英文短名（kebab-case）；项目没有 `docs/` 就先建。
- **同一功能在多个克隆里都有文档**时，只写当前仓这一份；别的克隆不复制、不跟改，需要共享时当前文档写一句「另一处只读引用本文」，各份同名文档 diff 必须保持为空或只差仓内路径。
- 文档状态机：`进行中` → `待定补充` → `可执行` → `已实现` → `已核对`。状态不由手写决定，按「落盘前自检」的计数与核对结论推导。
- 埋点、双语允许 `待定`；逻辑与 UI 每条都要有结论，接口未定也必须写清兜底。
- 后端契约里标「建议 / 候选 / 待核对」的值（消息类型号、字段名、content 结构）在文档里列为**阻塞项**，联调前必须回填；开发期间契约变了，当场回写文档与变更记录。
- 用户说「开始实现」→ 停，说明本轮只产出文档，执行另起一轮。

## 无信息就待定（硬约束）

PRD、后端契约、文案、埋点表、Figma 任一缺失时，**只记待定，不联想、不确认**。

- 缺什么就写 `待定（缺 X；归属：产品 / 后端 / 设计 / 埋点；补充后动作：…）`，并在待定项表里留一行。
- 禁止用「按常规 / 参考现有页面 / 先按默认值」把缺信息的字段写成结论。建议只能写在待定行里，不能作为结论。
- 后端没给取值清单、状态机、枚举时，状态映射一律待定。**禁止**自己把每个状态兜底成某个已知值（把评价卡片所有状态都映射成 `okay` 就是漏在这里）；不许拿近似枚举现编一套映射。
- 文案没有 key、没有中英文时写 `待定（缺文案 key）`，不拿现有相似文案顶替；埋点没有表时待定，不自己起事件名。
- 用户口头说「应该有 / 大概是」→ 记 `待定（口头，未落契约）`，不升格为结论。
- 每个待定项标阻塞级别：**阻塞开发** / **阻塞联调**（不影响写代码，上线前必须回填）/ **不阻塞**。
- 文档头部固定一行 `阻塞项：开发 <X> / 联调 <Y> / 不阻塞 <Z>`，数字从待定项表现数，改完待定项表当场重算，不凭印象。
- 状态与计数冲突时以计数为准：`X>0` → 进行中（或待定补充）；`X=0 且 Y>0` → 可执行（联调前回填）；`X=Y=0` → 可执行。手写的「可执行」被计数推翻时，改状态并在变更记录写一句。

## 改动边界（写文档时就质疑，先定改什么）

执行阶段改到意想不到的地方，是因为边界没写进文档。每个功能点开写前先查影响面，把边界落表：

1. **查调用方**：先用 codegraph（`codegraph_explore`）查目标符号 / 组件 / 状态映射函数的调用方与复用点；没有索引或查不到时，用 1 次定向 `rg`。只记录会因本次改动而变行为的调用点，不铺文件清单。
2. **先质疑**：把「按 PRD 这样改，会同时改到 N 个调用点 / 会改到共用组件 X / 共用映射 Y 会跟着变」写成一条提问，按四行格式给用户。一个功能点最多问 1 条范围问题，不把范围问题堆成清单。
3. **落表**：用户选定后写进 task 文档「改动边界」表。表外文件默认不许动。
4. **默认保守**：复用现有组件、现有状态映射、现有埋点上报点；不顺手重构、不抽公共组件、不改共用调用点的样式与默认值。要动共用点必须单列一行并写影响面。
5. **执行时守表**：只允许改标 `改` / `新增` 的行；其它文件出现 diff 算越界，必须回文档补一行决策再动手。

## 提问排版（硬约束）

发给用户的每个问题，必须按下面这种**空行分隔 + 标签加粗**的样式输出，不能压成连续四行：

这四行块不受 commander「≤3 条支撑」与「≤{{STYLE_MAX_LINES}} 行」预算限制（已作为字段块类结构列进 commander 硬约束第 1 条与 AGENTS「字段块输出」第 6 条）；每轮仍只问 1 题。

**问**：<一句话，落到字段或分支上>

**依据**：<代码或 PRD 里的证据：文件:行号 / 接口 path / 现有 key 或事件名>

**建议**：<用户不给答案时按这个走>

**备选**：<A / B / C>

成稿示例：

**问**：客服邀请卡片走 IM 消息还是后台推送？

**依据**：`chat_page` 已有自定义消息类型，客服侧来源未定。

**建议**：按 IM 消息发送，后台下发另立任务。

**备选**：A IM 消息 / B 后台推送 / C 两者都要

排版要点：标签用 `**问**` 这种加粗写法，不是 `问：`；四块之间各空一行；冒号用全角。本格式按字段块算（commander「字段块版式」第 8 条的例外：不加 `-` 前缀、块间空行），不受正文 ≤{{STYLE_MAX_LINES}} 行限制。

## 一轮做什么

1. **读文档**：已有 task 文档先读，已答项不重问。
2. **读现状**：确认 PRD 要的东西现在有没有、字段名、接口路径、现有 l10n key、现有埋点事件。
3. **列缺口**：PRD 与代码对不上的、PRD 没写但开发必须定的。
4. **只问 1 个**：挑最挡路的那一个，四行格式问完就停，等回答。
5. **回溯落盘**：收到回答后按下节回溯影响面，改正文、清队列、记变更。
6. **再问下 1 个**：同一轮里一次只推进一题，不连发。

每轮问答结束都要落盘，不要攒到最后一轮再写。

## 回答之后先回溯

用户的回答和补充信息可能推翻前面的结论，改文档前先做四步：

1. **圈影响面**：这次回答牵连哪些功能点、接口、字段映射、UI、埋点、文案、验收。
2. **改正文**：直接重写受影响字段，正文不留新旧两版；旧结论只进变更记录。
3. **清队列**：已作废的问题删掉，已失效的 `待定` 去掉或改写，新冒出的缺口排到下一题。
4. **记一笔**：变更记录写 `<旧结论> → <新结论>`，然后问下一个 1 题。

影响面到「目标与范围」就先改范围，再改功能点。任何一轮都不允许跳过回溯直接提问。

## 怎么提问

四个标签缺一不可，排版照上节。

- 能从代码或 PRD 读到答案的不问，先自己查。
- 不空问「要不要埋点」，问「这个曝光用现有 `xxx` 事件加参数，还是新增事件」。
- 不空问「权限要不要置灰」，问「次数用尽后还点，是静默不响应还是弹 `xxx` toast」。
- 不空问「选中什么效果」，问「点击瞬间就变色，还是等接口回包再变色」。
- 不空问「枚举会不会新增」，先查代码里现有映射，问「出现文档外的取值时丢弃还是只读」。
- 不空问「接口失败怎么办」，问「评价卡片详情接口失败时，是卡片内换成错误文案 + Retry（只重拉这一张卡），还是整页错误页」。
- 不空问「要不要重试」，问「Retry 点下去是单飞禁用还是允许连点；重试几次仍失败后给什么兜底」。
- 不空问「回包缺字段怎么办」，问「PATCH 只回 `permissions` 不回 `selection` 时，是保留本地选中还是清空；先合并权限再判业务字段吗」。
- 不空问「id 用哪个」，问「发送侧用 `peerId`、接收侧用 `conversationID`，这两个是否等值；不等就按哪个改」。
- 不空问「要不要缓存」，问「命中缓存还发不发 GET；同一对象 1 秒内触发 5 次请求用哪个键合并；登出时清哪些 key」。
- 不空问「有没有超时」，问「发消息等回执最长等几秒；超时后哪个字段复位，用户看到什么」。
- 用户答「不知道 / 后面给」→ 记 `待定`，写归属人和缺什么，继续下一题，不卡住。
- 用户答得含糊 → 追问一次；仍含糊就记 `待定（回答含糊）`，并写上建议默认值。
- 一次回答多个问题或额外补充信息：按影响面逐条落到字段，回溯后再问下一个 1 题。
- 同一问题问两次仍无结论，就按「建议」写进文档并标 `待定（按建议默认）`。

## 拆功能点

- 一条 = 一个入口 + 一个结果，用户能单独验收。
- `F1 / F2` 编号；跨两个页面或改动超过 3 个文件就拆子点 `F1.1`。
- 客户端与后端不拆成两条，后端依赖写在「数据来源与接口」。
- 接口失败态不单独成功能点，但每个接口都要在验收里留一条失败路径（断网 / 5xx / 超时）。
- 先列会改老行为的高风险项，再列纯新增。

## 四类问题清单

### 逻辑

必须写清：现状（文件:行号）、改什么、触发入口、数据来源（接口 method + path、请求时机、参数）、字段是新增还是改旧、字段→UI 映射、空数据 / 失败 / 未登录 / 重复点击、缓存与刷新时机、是否影响共用调用点、是否需要实验或灰度。

另外两条最容易漏，必须单独成句：

- **同值重复点击**：点已选项发不发请求、要不要客户端本地拦、拦下来给不给提示。
- **在途竞态**：同一对象「先读后写」（详情 GET 与提交 PATCH 并行）时，旧响应能不能覆盖新提交；用请求序号、在途标记还是丢弃过期响应，选一个写死。

### 功能与 UI

UI 和交互不能分开写：同一个元素既要有「长什么样」，又要有「点了会怎样」。每个功能点按三步做：

1. **列元素清单**：从三处反推这个页面该有哪些可交互元素——PRD 文案里提到的动作、Figma 帧里的区块与图标、现有组件里已有的按钮 / 选项 / 输入 / 滚动容器 / 弹窗 / 占位。一个元素一行，写在功能点开头。
2. **逐个过矩阵**：清单里每个元素都要在「交互状态矩阵」里有一行；缺一行不算完，也不允许用「同上」兼掉不同元素的差异。
3. **标资产**：每个图标 / 图片 / 插图按「UI 资产与图标」表写清来源，不留「用相近图标代替」。

必须写清：页面与区域位置、出现条件、布局结构（横滑 / 列表 / 固定高 / 弹窗高度）、间距与尺寸单位、复用的共享组件、加载 / 空 / 错误态、滚动与键盘、交互（点击 / 长按 / 滑动 / 返回 / 二次确认 / 提示）、可点热区、Figma 链接含 node-id。

样式与状态分开写：色值、边框、圆角只是「回包之后」的样子；点击瞬间、回包前、失败回滚不写就不算完，按下面「必填表」逐控件补齐。
接口层同样要过表：任何一次请求（含卡片内单独拉的详情、统计、推荐位）都要有失败落点、文案与 retry 结论，见「4. 接口失败与降级」。

**Figma 必读**：有链接且当前环境有 Figma 工具（figma MCP）就先读节点，把尺寸、间距、圆角、色值、字号、字重、图标名与 node-id 写进「布局」和「UI 资产与图标」；读不到（无权限 / 节点不存在 / 需要登录）就写 `待定（缺 figma 节点 <id>）`，不按 PRD 文字臆测像素。

**UI 复原的三个常见坑，必须在本节提前写死**：

- **图标拿错**：只允许三种来源——Figma 内图标（node-id）/ 仓库现有 asset 或 iconfont（文件:行）/ 需新增（尺寸、格式、命名）。没有第三种以外的自由发挥。
- **状态映射错**：一个后端字段的**全部**取值都要有视觉与可点性，不许只写正常态，也不许把未知值兜底成有效态，见「6. 状态 → 视觉映射」。
- **交互漏写**：元素清单里的元素与矩阵行数必须对得上；弹窗关闭、返回、滚动到底、键盘遮挡、二次确认这类非点击行为也算元素。

### 埋点（按 tracking-doc-format 联动，可待定）

必须写清：要不要、事件名（沿用还是新增）、上报时机、不报条件（去重 / 二次进入 / 折叠 / 未登录）、参数与取值来源、曝光口径（可见比例 / 停留时长）、上报通道、上报点。

按 tracking-doc-format 的版式与流程写，内容直接进 task 文档，见下节「埋点联动 tracking-doc-format」。PRD 带埋点表就按表落；没有就问归属人，先记待定，不自己起事件名。

### 双语（可待定）

必须写清：哪些文案是新增、是否用户可见、有没有现成 key、多调用点共用但只改当前点时**新增 key 不改旧 key**、key 命名建议、en / id 是否都要翻、占位符与拼接、日期货币格式、后端返回文案是否多语言。

按三类分别列 key，只写第一类就是漏：

1. **后端下发文案**：接口字段名 + 是否随 `locale` 参数变；后端不下发时的兜底。
2. **客户端兜底文案**：本地枚举兜底、空数据、未知值丢弃后的占位、单字段降级默认值——每个兜底分支都要有 key，缺了就 `待定（缺兜底文案 key）`。
3. **错误与提示文案**：网络失败、超时、业务错误码、权限不足、重试按钮各一行。

硬编码禁止：不允许在代码里写 `'Retry'`、`'OK'` 这类裸字符串，兜底文案也走 l10n。

## 必填表（任何可点控件、每个接口、每条异步链路都要过）

视觉写满了不等于状态写清了。单选、多选、互斥组、开关、提交按钮都要有前三张表；每个接口（含嵌套在卡片里的接口）都要有第四张表；任何图标 / 图片过第五张表；任何后端状态字段过第六张表；任何有写操作的接口过第七张表；任何跨端传递或拼 URL 的 id 过第八张表；任何会重复触发的请求过第九张表；任何等外部回调的链路过第十张表。缺表不算完成。

后四张（7–10）是本仓实测最容易出事的一组，「成功但字段缺」「id 用错」「请求风暴」「回调不回」都不算接口失败，前六张表兜不住。

### 1. 交互状态矩阵

每个控件一行：

| 控件 | 类型 | 点击瞬间 | 回包前 | 回包后 | 失败 / 超限 | 重复点已选项 |

- **点击瞬间**：乐观选中（立刻变色）还是等接口。若等接口，必须写清「点了看起来没反应」时靠什么告知已收到（按压态 / loading / 全组禁用）。
- **回包前**：能否再点其他选项、能否滚走、服务端数据此刻是否可被覆盖。
- **回包后**：回显取值以接口为准还是保留本地；返回的选中集与本地不一致时按哪边渲染。
- **失败 / 超限**：回滚到哪一版（点击前 / 上次成功），弹什么 toast，文案 key 是什么。
- **重复点已选项**：发请求 / 本地拦 / 取消选中，三选一写死；单选组点已选项等不等同取消，也要写。
- **多选**：有没上限、有没全选 / 清空、被拒后已选是否保留。
- **切组联动**：换档位、换 tab、换筛选时，另一组已选是清空还是保留（跨字段的联动最容易漏）。

### 2. 权限与容量字段两态表

后端下发的 `permissions`、`can_*`、`*_limit`、`*_count`、`expired`、`status` 一律不能写成「仅作参考」。每个字段一行：

| 字段 | 来源接口 | 为 false / 用尽时 UI | 还敢点时的反馈 |

- 「还敢点」必须给结论：静默不响应 / 弹提示（文案 key）/ 照发请求交给后端拒。
- 本地锁与后端拒绝的反馈要一致：不能一处置灰、一处静默，也不能本地拦了却不给提示。
- 客户端自行推导的锁定态（按 count 与 limit 算出来的）要写清推导规则，以及接口没传时的默认值。

### 3. 后端枚举与未知值策略

| 字段 | 取值 | 未知值处理 |

- 未知枚举默认**丢弃或只读**；禁止兜底成业务有效值（脏数据会冒充正常选择，图标、高亮、提交值全错）。
- 客户端硬编码映射的（图标、颜色、埋点参数）另写一句：后端新增取值时客户端表现成什么样。
- PRD 或方案若假设「枚举只会合并不会新增」，把它记进「风险与依赖」，不当作已知事实。

### 4. 接口失败与降级

每个接口一行，嵌在卡片 / 模块里单独拉的接口（评价卡片详情、商品卡统计、订单卡状态、推荐位）必须各占一行，不能只写页面级错误：

| 接口 | 失败落点 | 展示文案（key） | 重试方式 | 重试后刷新范围 |

- **失败落点**：整页错误页 / 区块错误 / 卡片内区域错误 / 单字段降级默认值，四选一写死。默认不允许「接口失败就整页报错」；卡片内接口失败还要写清卡片其余已渲染部分留不留、骨架要不要撑住高度。
- **展示文案**：主文案 + 副文案各自的 l10n key，不复用列表页错误文案；失败瞬间先显示什么（骨架 / 旧缓存 / 占位图）也写一句。
- **重试方式**：有没有 retry；入口在卡片内还是整页；retry 期间是骨架 / 按钮 loading / 全组件禁用；防连点（单飞 + 最短间隔）；重试次数上限，耗尽后给什么兜底。
- **重试后刷新范围**：只刷该卡片 / 刷整页 / 回列表；成功后是否清失败缓存、是否顺带刷新依赖它的字段（次数、角标、额度）。
- **自动重试**：下拉刷新、页面重新可见、网络恢复时是否自动重发，写一条；不写就是不做。
- **空 vs 失败**：200 + 空数据是空态，不是失败态，两者文案与 retry 按钮分开写。
- **业务错误码不走 retry**：无权限、已删除、已下架这类要给降级或跳转路径，不与网络失败共用一套文案。
- **抖动阈值**：慢网络下多久才显示失败态（避免骨架 → 错误 → 数据闪三次），写毫秒或写「不延迟」。
- **埋点**：失败与 retry 点击要不要上报，落到埋点节。

PRD 只写了「失败提示」四个字、没写落点与 retry 的，按上表逐行补问，不算已确认。

### 5. UI 资产与图标

每个图标、图片、插图、占位图一行：

| 控件 / 区域 | 复用组件（文件或类名） | 图标 / 图片 | 来源 | 尺寸与主题适配 |

- **来源只能三选一**：Figma 图标（node-id）/ 仓库现有 asset 或 iconfont（文件:行）/ 需新增（格式、命名、尺寸）。三样都没有就 `待定（缺图标来源）`。
- **禁止**「用相近图标代替」「从网上下一个」「先放个占位」，也不许自己命名后让开发去猜。
- 图标的选中态 / 禁用态 / 深浅色主题适配写在同一行；只给默认态不算完。
- 复用组件必须写清现有文件与类名；本次新写的组件单独标 `新增`，并写进「改动边界」表。

### 6. 状态 → 视觉映射

每个后端状态字段一行：

| 后端字段 | 取值（全部枚举） | 视觉（色值 / 图标 / 文案 key） | 可点性 | 上报 |

- **列全已知取值**，一行一个；必须覆盖 Loading、空、失败、无权限、已过期这类非正常态。
- **未知值 / null / 缺字段单独一行**，写「丢弃或只读」+ 具体表现（比如显示默认图标、不弹窗、不可点）。
- **禁止把未知值或未确认的取值兜底成业务有效态**（例如一律渲染成 `okay` 的绿勾）；取值清单没拿到就 `待定（缺后端枚举，阻塞联调）`，并在待定项表留行。
- 文案写 l10n key，不写死中文；同一状态在不同入口表现不一时拆行。
- 客户端自己推导的状态（比如按 count 与 limit 算出的锁定态）写清推导规则与缺字段时的默认表现。

### 7. 部分回包与字段缺失

「成功但字段没带全」比失败更容易写错：服务端只回 `permissions`、只回 `selection`、只回单个状态字段时，客户端是留旧值还是清空，必须逐字段写死。任何 `PATCH` / `POST` / 增量更新接口都要过一行：

| 接口 | 回包字段组合 | 缺失字段处理 | 是否允许覆盖本地新值 |

- 至少列「只带 A 不带 B」与「只带 B 不带 A」两种组合，没有这行就默认按整包替换实现，会丢掉刚拿到的新权限。
- **解析顺序**：先合并 `permissions` / 状态字段，再判业务字段（`selection` / 详情体）；禁止因为业务字段缺失就整包 `return` 原对象。
- **覆盖判定**：写清「回包版本 / 更新时刻 < 本地」时丢弃，还是以回包为准；在途请求与本地新写入谁优先。
- **列表与缓存同步**：单条更新后是否回写列表、是否重排、是否失效上级缓存。

### 8. 标识与外部输入

跨端传递、拼进 URL、当缓存 key、当消息定位键的值，全部过这张表（本仓历史 bug 高发区）：

| 标识 / 输入 | 来源字段（发送侧） | 接收侧同一个键 | 格式约束 | 编码与净化 | 缺失 / 非法时 |

- **发送与接收必须同一个键**：写清「发送用 A、接收用 B」是否真的等值；不确定就记 `待定（需一条真机日志对比）`，不假设相等。
- **消息定位键**：撤回 / 去重 / 排序 / 跳转各用哪个键（`conversationId + msgSeq` 还是 `messageId`），三处不一致就会错配。
- **URL 拼接**：id 必须 `encode`；长度上限、允许字符集、空白与控制字符的处理各写一句。
- **外部消息体**：接受哪些形态（字符串 / JSON 对象 / 数组 / 多层嵌套），异常形态是丢弃整条还是降级，禁止无边界的递归解析。
- **缓存 key 组成**：`<域>:<userId>:<id>`，写清跨用户隔离方式。

### 9. 请求预算与缓存生命周期

| 触发点 | 请求数 | 去重键 | 缓存 TTL / 新鲜度 | 清理时机 |

- **谁发起请求**：首次进入 / 列表变化 / 状态变化 / 回前台 / 下拉刷新逐个写；写清「状态变化是否重拉」，不写就实现成全量重拉。
- **命中缓存是否仍请求**：写死「命中即用」还是「命中仍刷新」；要刷新就写最短间隔与单飞（并发合并）。
- **去重键**：同一对象短时间多次触发用哪个 key 合并。
- **缓存生命周期**：写入时机、过期时间、容量上限、登出 / 切账号 / 会话结束 / 提交成功后各清什么；跨用户必须按 userId 隔离，禁止 `clearAll` 抹别的账号，内存态也要重置。
- **上屏策略**：先缓存后远端时，回包到达前渲染什么（骨架 / 缓存 / 空），到达后全量重建还是局部更新。

### 10. 等待外部回调的超时与恢复

每次「点了之后等别人回」的链路（HTTP、IM 发送回执、`Completer`、平台通道、动画结束）都要一行，只写 HTTP 超时不算：

| 链路 | 等待对象 | 超时阈值 | 超时后状态复原 | 用户可见反馈 |

- **超时阈值**：写秒数；队列丢弃、断网、后台挂起这些「永远不回包」的场景也要覆盖。
- **状态复原**：超时后必须在 `finally` 复位「请求中 / 禁用 / 单飞锁」，入口级锁最容易被永久卡死；写完指出复位字段。
- **用户可见反馈**：静默恢复 / toast（文案 key）/ 卡片内错误态，三选一写死。
- **重试与幂等**：超时后重发是否安全（有无幂等键）；不安全就只允许用户手动重试。

## 埋点联动 tracking-doc-format

写 `### 埋点` 章节时，按 tracking-doc-format 的版式与流程，但**产物落在 task 文档里**：

- **版式不变**：埋点名加粗独占一行；`**上报时机:**`；`**参数:**`；参数行 `- **name**: 类型。说明`；取值行 `  - 取值：<表达式>（文件:行）`。段间用 `-----------` 加上下空行。
- **逐条核对不变**：一轮只确认一个埋点，用户确认后再写下一个；对话里只给当前这一条 + task 文档路径。
- **不另建文档**：不生成 `docs/{{DOC_PREFIX}}<date>-tracking-<feature>.md`，也不在对话里另出埋点全文。用户明确说「埋点单独成文档」才走 tracking-doc-format 自己的落盘规则。
- **上报点就是边界**：每个埋点写 `上报点`——现有 `文件:行`，或 `待新增`（写清在哪个功能点的哪个入口）；上报点不在「改动边界」表里的文件，不得为了埋点改它的代码。
- **不编参数**：取值必须有代码依据（`rg` 上报 key 后读实参）；找不到写 `取值:未找到` / `待实现（候选 X）`，不拿近似字段冒充。
- 埋点表本身没拿到时，先记待定，不用假设参数把章节填满。

九项同时满足才能把状态改成「可执行」：

1. 每条功能点的逻辑、UI、验收都有结论；无信息的项已写待定，且没有「阻塞开发」的待定项。
2. 改动边界表每个功能点至少一行，`改` / `新增` / `禁止` 都写明；影响面来自 codegraph 或定向搜索，不靠猜。
3. 每个元素清单里的控件都有交互状态矩阵行；每个图标都有来源（Figma node-id / 现有 asset / 需新增），没有「相近图标」。
4. 每个后端状态字段都有「状态 → 视觉」全枚举映射，未知值有丢弃或只读结论；没拿到后端枚举就不能标可执行。
5. 埋点按 tracking-doc-format 版式写进本文档，每个埋点都有上报点与取值依据；没拿到埋点表就是待定。
6. 每个接口都有失败落点 / 文案 / retry / 刷新范围；验收每条都是「点什么 → 看到什么」，且每个接口至少一条失败路径。
7. 每个有写操作的接口都有「部分回包与缺失」行，并写明解析顺序（先权限/状态，后业务字段）。
8. 每个跨端 id 都有「标识与外部输入」行：发送与接收同一个键、编码、异常形态、缓存 key；不确定的写成待定而不假设相等。
9. 每个会重复触发的请求都有「请求预算与缓存」行（去重键 / 缓存新鲜度 / 清理时机 / 跨用户），每条等回调的链路都有超时与状态复原。

不满足就保持「进行中」或「待定补充」，并在回复首行点名阻塞级别最高的那几项。

## 实现核对（用户说已实现 / 要求审核时）

文档写完不等于代码照做了。用户说「已实现 / 审一下 / 有没有漏」时走本节，只读不改：

1. **定位**：先读文档「改动边界」表，按表逐行 `rg` 找真实落点（`文件:行`）；表里没有的改动记一条越界。
2. **逐表核**：按必填表 1–10 逐行核代码——交互矩阵看 `onTap` 与禁用条件；权限表看 `can_*` 是否真被拦；枚举表看未知值是否兜底成有效值；部分回包看解析顺序；标识表看发送/接收键是否一致；请求预算看有无重复拉取；超时表看 `finally` 是否复位。
3. **编号输出**：`W-001`（会导致错误行为）/ `I-001`（不一致或待确认），每条一行：现象 + `文件:行` + 按文档应该怎样；同一轮先给出编号清单，等用户挑，不自己开修。
4. **冲突判定**：代码与文档不一致时，先判「实现对还是文档对」；文档错就当场回写文档（变更记录写 `<旧结论> → <新结论>`），实现错才列 W。
5. **收尾**：核完把每个功能点状态改为 `已实现`（代码有、未逐项核）或 `已核对`（逐表核过、W 项已清），并在「风险与依赖」记未清项。

## 后续补充

- 用户给出埋点或文案后：只改对应章节，`待定` 改成结论，同步待定项表和变更记录，重判状态。
- 执行阶段出现表外改动：停下，把该文件补进「改动边界」表并写明决策来源，再继续；不靠口头默许扩大范围。
- 开发期间后端契约或产品口径变了（字段名、消息类型号、content 结构、状态机、枚举取值）：立刻回写受影响的功能点、必填表、改动边界与变更记录，变更记录写 `<旧结论> → <新结论>`。
- 开发后回补：把已修的 bug 按「漏了哪张表」归类，补到对应章节，下次同类需求直接照表填；漏的表在完成条件里加一句同类检查。
- 换会话继续：先读 task 文档头部（状态、阻塞计数）与待定项表，再读「变更记录」最后几轮，从第一个未完成字段接着问，不让用户重答。
