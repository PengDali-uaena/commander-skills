# reply-brief

把答案收成能直接读的文字：先整合结论，再删掉读者不需要的部分。版式按读起来顺不顺来定——一段说得清就写段落，并列项写列表，对照或多列事实写表格。不套固定字段名。

若本目录有 `{{SKILL_DIR}}learned.md`，先读它；其中与这次问题相符的偏好覆盖下面默认。

本文件只定「说什么、说几句」。首句加粗、并列项各占一行、去裸 URL 与绝对路径这类排版收口按 AGENTS「可见回复」与 commander 硬约束执行，不在这里重写一遍。

## 公共边界

- 不写「结论：」「依据：」「边界：」这类固定行首；不在每段末尾追问「是否符合预期」。
- 一条消息里多个问题按**提问顺序**各答一句，再补一条共同证据；不按代码结构重排。
- 路径、数字、Tag、报错原文在支撑结论时写全，不支撑结论的过程和文件清单删掉。
- 不主动搜仓库、不加日志、不改代码。用户同条明确要求改代码时：先把答案写完，再改。
- 推翻自己上一轮判定的说法，按 `commander` 的「改口作废」处理，不在这里复述。
- **只答被问的那一条**：评估 / 排查 / 审计轮次里想到的其他改动（别的 tab、别的场景、别的分支），一律不写进结论；确实相关时在末尾单独一行 `- 可选项·未确认不动：<一句>`，不动手、不展开方案。

## 根因 + 修复建议（用户点名两栏时）

用户消息里同时出现「根因」与「修复建议」（或同义，如「原因 + 怎么办」），且**未**要求展开、日志、筛选、验 API、部署步骤时：

- 可见回复 **仅两行**（或两段各一句），行首用 **「根因：」** 与 **「修复建议：」**（用户指定别的标签就用用户的）。
- 根因一句说清**为什么**；修复建议一句说清**下一步**（数据 / 配置 / 重部署 / 找谁），不展开多方案。
- **禁止**：表格、编号清单、cURL、字段 JSON 示例、DevTools 自检、文件路径、组件挂载链——除非用户下一条说展开。

读仓与 curl 在工具过程里做，结论压进上述两句，不把调查过程贴进可见回复。

## 有没有实现 / 核对上轮（默认）

用户问「有没有实现」「不是说…吗」「强插了吗」等，是在核对**已有承诺**而非要新方案时：

- **第一句直接答**：有 / 没有 / 只有部分（选最准的一个）。
- **第二句**一句说明条件或遗漏（例如「只在 DEV」「接口缺字段」）。
- **禁止**：表格、变更文件列表、URL 参数大全、重部署教程——除非用户追问。

## 是否 / 同一性题（默认）

用户只问「是不是 / 一样吗 / 同一个吗 / 是否同一套」且未说展开、挂载、流程时：

- **第一行先答是或否**（或「不完全是」等直接结论）。
- 正文 **总共 1～3 句**；证据最多 **一个**类名，或 **一条** `A → B` 引用链。
- **未点名的页面、模块、场景不主动对比**（例如只问详情 vs checkout，就不要展开其它入口）。
- 文末最多一行：`要讲挂载/引用链 code-logic 或让我展开。`

## 追问轮（同一话题第 3 轮起，或用户说「仅回复是不是即可」）

- 只答被问的那一点；前面已解释过的前提不重述。
- 用户说「仅回复是不是即可」→ 按提问顺序 `1./2./3.` 逐条给 `是` / `不是` / `是，但…`，每条一行，不解释。

## 审计盘点型

用户问「这个模块合不合理 / 有没有缺陷 / 数据都展示了吗」，没给 diff、没要求出报告：

- 第一行给判定（合理 / 有 N 处实质缺陷 / 结论不成立），第二行一句最该先知道的事。
- 缺陷最多 5 条，每条一行：位置 + 现象 + 后果；超过 5 条只留最严重 5 条，其余写「另 N 条可展开」。
- 正文总共 ≤ 20 行；不写通过项、残留风险、修复建议清单，除非用户点名要。
- 可借用项目 review skill 的检查方法，但输出按本节，不按它的模板。
