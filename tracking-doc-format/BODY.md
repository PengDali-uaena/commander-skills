# tracking-doc-format

把下载的埋点文档（`.csv`）整理成按埋点 key 分段的可读文本。只做格式归一：不改埋点名、不加参数、不推断没写的时机与说明。

若本目录有 `{{SKILL_DIR}}learned.md`，先读它；其中的**版式**偏好（加粗、缩进、空行、分割线位置、颜色禁用等排版细节）覆盖下面默认，但**不得覆盖步骤顺序与默认模式**——逐条核对 / 全篇输出的判定权只在本文件的步骤 6、7。

`learned.md` 的边界（写文件前先判）：

- **只允许记版式**。落盘路径、逐条还是全篇、要不要写文件这类流程句一律以本文件为准，`learned.md` 里出现同类句子直接忽略，并在本轮回复末提一句「learned.md 里的流程句已失效」。
- **结论会过期**：`learned.md` 里的取值锚点（哪个字段、哪一行）只作线索，每轮必须 `rg` 复核；与本轮确认的结论冲突时以本轮结论为准，并当场改 `learned.md` 那一行，不留两套说法。
- 两侧各有自己的 `learned.md`，`dist.mjs` 不生成、不校验它；不往里面抄事件清单或参数表（会与落盘文档分叉）。

## 触发

用户给出埋点 `.csv` 路径、或直接贴了 CSV 内容，要求「整理 / 格式化 / 按 key 分段 / 这样展示」。用户贴出示例样式时，以用户示例为准，本文件只补默认。

也用于开发后回看：已经实现完、要核对「埋点是否实现完 / 参数对不对 / 有没有漏」，走本文「实现核对」，不重出埋点表。

## 被 prd-to-task 调用（联动模式）

prd-to-task 写 `### 埋点` 章节时走本 skill 的版式与逐条核对，但**产物落在 task 文档里**：

- 输出写进 task 文档的 `### 埋点` 章节；不落盘 `docs/{{DOC_PREFIX}}<date>-tracking-<feature>.md`，也不在对话里另出全文；对话只给当前这一条 + task 文档路径。
- 逐条核对不变：一次一个埋点，确认后再下一个；全部对完也不再单独给全文（全文就是 task 文档里那一节）。
- 每个埋点额外一行 `- **上报点**：<文件:行> 或 待新增（<功能点 / 入口>）`；上报点必须在 prd-to-task 的「改动边界」表里，不在就记待定。
- 版式、加粗、取值溯源、反例规则全部不变。
- 用户说「埋点单独成文档」时退出联动模式，按下面「输出位置」落盘。

## 步骤

1. **取数**：`read` 用户给的 csv（不要 `cat` 全量打印到回复）。用户直接贴内容时按贴的解析。
   - 非 csv 形态：`.xlsx` 先要求导出 csv；在线表（Google Sheet / 飞书）要求导出或贴表；PDF / 截图里的表格不作为唯一依据，只能按可读行解析，并在回复首行注明「来源非 csv，可能丢列 / 合并单元格，请核对」。
   - 合并单元格、跨行事件名、空行分隔多表：按列位置套用「向下填充」；同一份同一事件出现两张表时按出现顺序拼接，不合并段。
2. **切段**：埋点文档常见是「一个埋点占多行，只有首行写埋点名与上报时机，后续行只写参数」。
   - 埋点名列非空 → 新开一段；空 → 归上一段的参数行（向下填充）。
   - 连续多行埋点名相同 → 合并成一段。
   - 一行一个埋点、参数挤在单元格里（用换行 / `；` / `、` 分隔）→ 先按分隔符拆成参数行再整理。
3. **识别列**（按表头关键词，命中即用）：

   | 用途 | 表头关键词 |
   |---|---|
   | 埋点名 | 埋点名、事件名、事件、event、event_name、埋点key、key |
   | 上报时机 | 上报时机、触发时机、触发条件、上报说明、场景、时机 |
   | 参数名 | 参数名、参数、字段、param、属性 |
   | 类型 | 类型、参数类型、数据类型、type |
   | 说明 | 说明、描述、含义、备注、desc |

   **产品表常见列（Event Track - By Version）**：`场景` 多为段标题或人读标签，不当作埋点 key；`事件(Event)` → 埋点名；`参数(Parameter)` → 参数名；`取值(Value)` 常为类型或类型+约束（并入类型/说明，不单独当「取值溯源」）；`备注(Remarks)` → 说明，且首行参数常含上报时机原文。该表无独立「上报时机」列时，从首条参数的备注取用；仍空则写 `上报时机:未注明`。

   表头对不上时按列序兜底（第 1 列埋点名、第 2 列上报时机…），并在回复首行写明「按列序识别」，请用户确认。识别不到的列直接丢弃。
4. **清洗**：去首尾空白；单元格内换行并成一句；`string` / `int` / `bool` / `json` / `string[]` 沿用原文，后面统一接「类型。」（原文本就写「string类型」时不要重复）。
5. **取值溯源（必做，除非用户说只要格式）**：每个参数都要落到「值从哪来」，不能只有类型和说明。
   - 先在工程里搜埋点 key（`rg -n "<event_key>" lib`）。找到上报点 → 读那次调用的实参，把字段/表达式原样写进取值，并带 `文件:行`。
   - 没找到上报点（埋点还没实现）→ 去读该业务的数据模型与组件，给出现状可直接用的字段；确实没有对应字段就明说「需后端下发」，不要拿近似字段冒充。
   - 不确定的写 `取值:未找到` 或 `待实现（候选 X）`，禁止编造字段名。
   - **上报点必填**：每段埋点写一行 `- **上报点**：<文件:行>`；没实现写 `待新增（<功能点 / 入口>）`，猜不到入口就写 `待实现`。已实现的埋点不写上报点等于没核。
   - **参数上限校验**：若原文或文档里写到 Firebase「25 个参数」上限，或该事件已有实际上报点，统计「该事件既有参数数 + 本次新增」；合计 > 25 时在该段末尾写 `参数数：<既有 a> + <新增 b> = <合计>，超过上限，需合并或舍弃` 并在回复首行点名，不静默略过。
6. **逐条核对（默认，不可跳过）**：按下方「版式」**一次只输出一个埋点**，等用户确认后再出下一条；**禁止**在一条消息里连发两条，**禁止**一次倒出全文。`learned.md` 不得覆盖本步：即使其中记录「整篇一次给完」，也只在用户本条明确要求全篇时生效。
   - 开头一行写进度与状态，不只写序号：`共 N 个埋点，第 3/N｜已确认 2，跳过 1（pdp_video_watch_end），待定 0`。
   - 用户说「对 / 可以 / 继续 / 下一个」→ 出下一条；用户指出错处 → **只重出这一条**，已确认的段不重出。
   - 用户说「跳过 / 先跳过这个」→ 记入跳过清单，**当场写下一条**，并在后续每轮进度行里列出跳过项；不得因为跳过而漏掉清单。全部走完后单独问一句「跳过的 N 条还补吗」。
   - 用户改口径（去参数 / 改取值 / 改上报时机）→ 只重出这一条，已确认段不动；同一项被反复改口时，以**最后一次明确说法**为准，并在核对记录里写 `<旧> → <新>`。
   - 跨会话继续：若文档已落盘，先读其末尾「核对记录」表，从第一个非「已确认」的行接着问；没落盘就以上一轮进度行为准，不重头问。
   - 写完当前这条就**停**，把确认权交回用户。
7. **出全文**：全部埋点都对完后，才按版式把整篇输出一次；段与段之间一条 `-----------` 加**上下各一空行**（共两个换行）。逐条阶段**不加**分割线，`-----------` 只出现在全篇里。全文末尾固定附「核对记录」与「口径修订记录」两节（见下），这两节也是后续实现核对的入口。

## 版式

每个逻辑块**独占一行**；块与块之间**必须空一行**。禁止把多段拼进同一段落。

**加粗是硬要求**：埋点名、`**上报时机:**`、`**参数:**`、每个 `**参数名**` 必须用成对的 `**`（ASCII），不得用单反引号 `` `pdp_xxx` `` 代替标题或参数名。本 skill **不受** User Rules「加粗 ≤5 处」限制。

**分割线**：只在**全篇**输出时出现——段末下一行必须是且仅是 `-----------`，上下各空一行，全文禁止省略；**逐条核对阶段单段输出不带分割线**。

**缩进（Cursor 对话必用列表，否则看不见层级）**：在 `**参数:**` 下每个参数两条列表项——

```
**show_card**（卡片曝光）

**上报时机:** 卡片可见时上报，同一页面内不重复上报，刷新页面重置上报逻辑

**参数:**

- **module_name**: string类型。选择当前卡片后端下发的 title 来作为参数

  - 取值：product.title（product_detail_v3_model.dart:134）

- **rank**: int类型。当前的位置，从1开始。

  - 取值：_photoIndex + 2（pdp_video_header.dart:737）

- **上报点**：pdp_video_header.dart:737；未实现写 待新增（F1 讲解视频曝光入口）

-----------

（全篇里的下一段…）
```

- 列表：参数行用 `- **name**: 类型。说明`；取值行用空一格的 `  - 取值：…`（2 个空格 + `-`），**单独一行**，格式 `取值：<表达式>（<文件>:<行>）`；多来源用 ` / ` 分隔。
- 每段末尾一行 `- **上报点**：<文件:行>` 或 `- **上报点**：待新增（<功能点 / 入口>）`；它与参数行同级、不加缩进。
- 不用纯空格缩进代替列表（Cursor 对话里空格缩进常被吞掉）。
- 说明缺失时只写类型，不留空冒号；上报时机原文为空时写 `上报时机:未注明`。
- 参数顺序、埋点顺序按原文，不排序、不去重同名不同义的参数。

## 核对记录与口径修订（固定两节）

全篇末尾固定两节，逐条阶段不贴；落盘后它们就是跨会话续接与实现核对的唯一入口。

```
## 核对记录
| # | 埋点 | 状态 | 轮次 | 用户确认原话 |
| 1 | pdp_video_exp | 已确认 | 3 | 「其他没问题，下一个」 |
| 2 | pdp_video_watch_end | 跳过 | 4 | 「也跳过」 |
| 3 | pdp_video_load_result | 待定 | 6 | 「等后端给枚举」 |

## 口径修订记录
- <埋点>：<旧口径> → <新口径>（第 N 轮）
```

- 状态只用 `已确认` / `跳过` / `待定` 三种；被改口的先记 `待定`，用户再次确认才转 `已确认`。
- 每轮确认后立刻更新这两节（没落盘就先在进度行里反映），不攒到最后一次写。

## 强调（不用颜色）

终端和对话通道都不支持给文字上色（裸 ANSI 的 ESC 会被剥掉，HTML span 会原样显示），所以全文只用加粗拉开层次，不要写颜色、不要写 span、不要写 ANSI：

- 埋点名：加粗，独占一行
- 「上报时机:」「参数:」：加粗标签本身
- 参数名：加粗

落盘的 `.md` 与对话正文使用**同一套**纯加粗 Markdown，不引入 HTML。

## 反例（禁止）

下面这种是**错误输出**，不得出现：

- 整行只有 `` `pdp_video_watch_end` `` 或 `pdp_video_watch_end`，没有 `**pdp_video_watch_end**`
- `上报时机:`、`参数:`、`product_id:` 未加粗，或与说明糊在同一段落里
- 段与段之间没有 `-----------`
- 用反引号高亮参数名，代替 `**product_id**`
- 取值与参数挤在同一行、无 `  - 取值：` 子项

## 发出前自检（正文写出前在心里过一遍）

1. 每个事件名是否都是 `**event_key**`（可带中文括号说明）？
2. 是否每两段埋点之间都有 `-----------` 且上下空行？
3. 每个参数是否都有 `- **param**:` 与 `  - 取值：` 两行？
4. 每段是否有 `- **上报点**：`？
5. 是否没有用代码围栏包住全文？
6. 逐条阶段是否**只**有当前一个埋点、结尾停在等用户确认（没顺手带出下一条、没提前给全篇）？
7. 进度行是否带已确认 / 跳过 / 待定计数，跳过项点名到 key？
8. 有没有写颜色、span、ANSI、单反引号当标题？

## 实现核对（用户说已实现 / 要求审一下时）

用户问「看埋点是否实现完 / 有没有漏 / 还有其他 bug 吗」时不重出埋点表，改为核对代码：

1. **建表**：按落盘文档的埋点清单逐条建行，不按代码现有上报点反推（后者会漏掉未实现的事件）。
2. **逐条比四件事**：上报点是否存在（`rg`）；参数是否齐全且类型一致；取值表达式是否就是文档写的那一个；上报时机（首次 / 每次切换 / 退出 / 去重）是否一致。
3. **编号输出**：`W-001`（会导致错报 / 漏报）/ `I-001`（不一致或待确认）。每条一行：现象 + `文件:行` + 按文档应该怎样；先交编号清单、等用户挑，不自己批改。
4. **冲突判定**：代码与文档不一致时先判「实现对还是文档对」；文档错就当场回写文档（进「口径修订记录」），实现错才列 W。
5. **回写**：核完把已实现的上报点填进文档 `**上报点**` 行（`待实现` → `文件:行`），并在核对记录里把对应埋点标 `已确认`；未实现的列进「待补实现」清单。

## 不要做

- 不改埋点名拼写、不合并两个埋点、不补原文没有的参数。
- 不翻译说明文字（原文中文保持中文，印尼语/英文同理）。
- 不把参数类型改写成代码类型（`int类型` 不写成 `int`），除非原文只有类型没有「类型」二字且用户要求保留原样。
- 不加分析、不加建议、不排序，也不在段间加小标题。
- 不编取值：没读到代码依据的参数，只能写 `取值:未找到 / 待实现`，不许拿同名或近似字段顶上。
- **禁止**用代码围栏（```）包裹全文或整段埋点（会破坏对话里的 Markdown 渲染）。

## 可见回复

本 skill 的**分段正文**不受 commander「≤{{STYLE_MAX_LINES}} 行」「加粗 ≤{{STYLE_MAX_BOLD}} 处」限制（与 prd-to-task 字段块同类）；仍须遵守版式里的**空行与缩进**。

- **首行**：一句结果（段数；若有列序兜底或缺上报时机一并写明），再接进度行 `共 N 个埋点，第 i/N｜已确认 a，跳过 b（<key>），待定 c`。
- **逐条阶段**：正文只放**当前这一条**埋点，按版式写全；写完停，问一句「这条对吗 / 继续下一条」。不预告后面的段、不给摘要、不说「全文见下轮以外的地方」。
- **全篇阶段**：全部确认完才按版式在对话里给**全文**（含「核对记录」「口径修订记录」两节），段间 `-----------`，不截断、不省略段；给完问一句「要不要落盘到 `docs/{{DOC_PREFIX}}<date>-tracking-<feature>.md`」，**用户下一条明确同意或点名落盘**再写文件（路径见「输出位置」），本轮不得擅自落盘。
- 只有用户明确说「直接给全文 / 一次给完 / 不用一条条对」才跳过逐条，直接全篇。
- **实现核对轮**：不重出埋点表；先给 W/I 编号清单（最多 5 条 + 一句总数，每条带 `文件:行`），等用户挑。

## 输出位置

1. **默认**：先在对话里输出全文（供用户在当前会话里审阅、修改意见），不直接落盘。
2. **落盘路径（固定）**：用户明确说「写成文档 / 落盘 / 导出 / 存成 md / 确认保存 / 写到文件」时，写入当前仓库的 `docs/{{DOC_PREFIX}}<date>-tracking-<feature>.md`：
   - 文件结构：标题 + 来源与整理时间 + 埋点分段（段间 `-----------`）+ 「核对记录」+ 「口径修订记录」。
   - 已有同名文件时先读旧的「核对记录」，只改差异段并补修订记录，不整份重写、不丢旧结论的来源。
   - `<date>` 用 `YYYYMMDD`（如 `20261113`）；<feature> 用英文短名 kebab-case（如 `pdp-video-perf`）。
   - 工程没有 `docs/` 目录时先建；cwd 不在仓库内时问一句落到哪个仓。
   - 不再用「与 csv 同目录的 `<原文件名>-format.md`」旧规则。
3. 用户明确「不要写文件 / 只要对话」时，本轮及后续同任务都不落盘。
