# spec-features

把用户给的背景（想做什么、为什么、担心哪里会改坏）压成**可逐条执行的修改功能点**。用户先拿这份清单核对，再决定要不要让 AI 动手。

**只在用户显式 `spec-features` 或点名时使用**：不进 commander 产物表，不参与自动路由，也不转交其它 skill。

## 不做什么

- 不读仓库、不查文件、不改代码、不加日志、不写文件。
- 不评估可行性、不比较方案、不给实现步骤。
- 背景里没有的功能不编；推断出来的单列，标明「推测」。
- **不越界**：本条背景没提的场景（其他 tab、其他分支、其他实验组、其他页面）不进功能点，最多在结尾「未纳入」一行点名；不替用户决定了改别的。

## 执行

1. **对齐**：一句话复述目标（≤40 字）。意图明显跑偏时先点出来。
2. **拆点**：只输出功能点清单，一条一个点。
3. **收尾**：一行「按这份清单实现吗？」，不写总结段。

## 功能点写法

一行一条，`-` 开头，每条只写**做什么**；不写改哪块，不写完成标准。

- 每条 ≤150 字（中文按字算，含标点）；写不下就拆成两条，不缩句硬凑。
- 一条只做一件事；出现「并且 / 同时」就该考虑拆。
- 动词开头：新增 / 修改 / 删除 / 调整 / 限制 / 支持，让用户一眼看出是改行为。
- 保留用户原话里的名词（功能名、页面名、字段名），不改写成同义词。
- 不写「优化体验」「提升性能」「更流畅」这类没有落点的词。
- 排序：先写会改变现有行为的高风险项，再写纯新增，同类相邻。

## 待确认

背景里自相矛盾、指代不明、缺边界条件的地方，放在清单之后；以「待确认：」起一行，最多 5 条，每条一句问句。没有就整节省略。

## 未纳入

本条背景之外的改动（别的 tab / 分支 / 场景，或用户之前没让改的部分）集中写在这一节，一行一条、只说不动手。没有就整节省略。

## 可见回复

- 不写小标题、不写「结论：」；顺序固定：对齐句 → 清单 → 待确认 → 未纳入 → 确认句。
- 不列验证清单，不交代命名、常量、注释这类实现细节。
- 条目数不设上限；背景撑不起 3 条就只写 1～2 条，不凑数。
